## 一、综合结论（先看这节）

1. 网上**没有与本项目一模一样的整套工程教程**——「银行流水→数据中台→金蝶自动制证→对账留痕 + 内网独立部署」是高度定制化的私有落地。
2. 但**按环节分段，参考相当充足**；多数来源印证了本项目的核心选型与做法：
   - 银企流水自动生成金蝶凭证（数环通、成集云）——与一期同路线；
   - 「字段清洗—规则匹配—异常分流—余额调节—凭证联动—审计留痕」闭环（实在智能）——与 R001~R006、WARN 转人工、aud 哈希链对应；
   - 批次勾稽「期初+Σ收支≈期末」（bankstatementparser / Excel running balance）——即 R006 实现基准；
   - 金蝶 WebAPI 认证与报文（**官方 OpenAPI 含 Python SDK** + YiKdWebClient 报文）——是 Mock→真实推送的权威对照。
3. **可直接使用的仅有开源库**（bankstatementparser 等）；其余多为方法论参照、商业方案印证、报文参考，需自行翻译为 Python + 本项目分层契约。

## 三、按本项目环节的建议借鉴映射

### 1. 数据采集（银行侧）
- D3 银行 API 凭据未就绪 → 当前 Mock 合理；真实对接时**先跑通认证/验签**再谈数据（对齐 B2 强调的「接口/登录策略决定成败」）。
- 网银/文件采集的流程可参考 B1（登录→查→下载流水→回单）。

### 2. 字段清洗与统一契约
- **最值得直接引用：C1 bankstatementparser**——多银行格式统一为单一 `Transaction` 模型，正是你「落地比对-v1」的基准；C3 提供更多银行/格式的解析参考。
- 中文字段/借/贷/币种清洗可参考 C1 与 B1 的字段标准化手法。

### 3. 规则校验 R001~R006
- **R006 批次余额勾稽**：C1 的 Golden Rule + B5 的 running balance 思路即「期初+Σ收入−Σ支出≈期末」，本项目已落地。
- 异常分流（WARN 转人工、REJECTED/LOADED 语义）：对齐 B2 的「异常池」与「先落库留痕」。

### 4. 科目规则预填（决策 P1）
- A1/A2 商业方案都实现「按账户/组织/交易类型/对方户名映射科目自动带凭证」——印证 P1 方向。
- 规则表（关键词/正则/方向优先级）设计参考 C1 的 account_mapper 能力。
- 手段可参考 **F1（AccountMatcher 关键词/语义规则库）、F5（摘要关键词+金额方向→科目例表）**；
  也可参考 **F6 金蝶AI-凭证模板**的三种取值（固定值 / 科目影响因素 / 单据科目字段），把科目判定放到金蝶侧的凭证模板里，减少我方映射面。
- 高质量科目来源：F2/F3 的「对方户名/收支类型智能识别匹配既有科目」，配合 P4 财务维护的银行存款科目映射表。

### 5. 推送金蝶与自动制证（工作包 6，挂起中 B1）
- **核心参考 D1 YiKdWebClient**：
  - 认证方式：第三方登录授权 AppSecret、API 签名 SHA1(8.0.0.202205 前)/SHA256、集成密钥 .cnf 护照；
  - 免登录验证的「API 请求头签名」可大幅减少请求次数，适合定时日切；
  - 制证对应 `BatchSave`（记账凭证）、查单 `ExecuteBillQuery`、`Audit/Submit`；
  - 多账套/多集成用户用参数化 `AppSettingsModel` 动态初始化 → 呼应本项目「凭据环境变量注入、多环境切换」约定。
  - **不可直接引代码**（.NET 栈与 Python 后端冲突），仅迁移协议；报文结构以 D2 那本接口说明书 + postman collection 为全字段对照。
- **① 官方 OpenAPI 体系（首选，与本项目 Python 栈匹配）**：
  - 官方接口为 HTTP+JSON（RESTful），提供 **18 个标准接口 + 1 自定义接口**；官方提供 **.NET / Java / Python 三种 SDK**（E1）——有 Python 官方 SDK，可优先采用而不是自己写 HMAC。
  - 凭据/流程：第三方系统登录授权在 `open.kingdee.com` 完成（获取应用 ID/密钥），接口文档与 SDK 在 `openapi.open.kingdee.com`（E3/E4）。
  - 若需绕开 SDK/精简依赖：可自实现 **HMAC-SHA256 签名**（时间戳随机数→待签名字符串→HMAC-SHA256→Hex→Base64→请求头），见 E2 实战文——契合本项目`零外部依赖`约定，且与 D1 的「API 请求头签名」互为印证。
  - 制证端点：`BatchSave`（记账凭证批量保存）、查单 `ExecuteBillQuery`、`Audit/Submit`，接口版本时间线见 E5。

### 6. 复核工作台与审计留痕
- C2 的 human-in-the-loop、阈值以上自动勾选 → 你的「复核台 + R004 超阈值转人工」同源。
- B2 强调的审批归档 + 完整审计证据链 → 对应本项目 aud_audit_log 哈希链与双向溯源。

### 7. 部署与隔离
- 无新意来源；按项目硬约束（独立 MySQL 8.0 + 独立内网 + Docker Compose + 凭据密钥服务注入）执行即可。

## 四、YiKdWebClient 专题（阅读结论）

**定位**：C#/.NET 库，纯 HTTP 实现金蝶云星空第三方 WebAPI；移除官方 SDK 与 Newtonsoft.Json 依赖；兼容 .NET / .NET Framework / netstandard；含 SSO 单点登录（V1~V4）与自定义 WebAPI（stubpath）。

**能否借鉴/使用**：
- ✗ 不能直接使用：语言栈为 .NET，与项目「Python/FastAPI + 内网零外部依赖 + 统一后端」冲突，引入 .NET 运行时不可取。
- ✓ 协议层高度可借鉴，直接服务 B1（金蝶真实推送/自动制证）：
  1. **认证方式全集合**：第三方登录授权(AppSecret) / API签名(SHA1/SHA256) / 旧用户名密码 / 集成密钥(.cnf)。
  2. **API 请求头签名**：不调登录验证接口，请求次数大幅降低 → 适合定时批量推送。
  3. **接口清单**：`Save/BatchSave/Audit/Submit/View/ExecuteBillQuery/Draft/ExecuteOperation/Push/AttachmentUpload/GetSysReportData` 等 → 自动制证端点为 BatchSave、查单为 ExecuteBillQuery、审核为 Audit。
  4. **动态初始化**：多账套/多用户用 `AppSettingsModel` 参数注入（非静态配置）→ 契合本项目凭据经环境变量/密钥服务注入、多环境切换。
  5. **报文权威对照**：仓库内《金蝶云星空WebAPI接口说明书_V6.0.docx》+ `星空WebAPI.postman_collection.json.zip` 是把 Mock 落成真接口的字段级标尺。

**落地到本项目的行动建议**：在 `backend/app/services/kingdee.py` 中，把当前 Mock 推送升级为「真实报文构造 + 金蝶签名 + BatchSave 制证」，报文字段以 D2 为准；凭据就绪（B1 前置依赖）即切换。此项属 9/16 链路打通的关键路径。
