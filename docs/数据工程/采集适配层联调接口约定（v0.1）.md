## 二、统一流水契约（单条流水 JSON）

> 契约核心八字段（对齐执行方案 v3 §8.3，契约冻结 8/27 回填 C 系列确认项）。

```json
{
  "txn_no":              "CMB202608240001",
  "txn_date":            "2026-08-24",
  "txn_time":            "10:23:45",
  "currency":            "CNY",
  "amount":              15000.00,
  "dc_flag":             "C",
  "counterparty_name":   "某某科技有限公司",
  "counterparty_account":"6222020200xxxx",
  "summary":             "货款"
}
```

| 字段 | 类型 | 必填 | 说明 | 落库列 |
|-|-|-|-|-|
| txn_no | string | 是 | 银行唯一流水号 | dwd_trans_flow.txn_no |
| txn_date | date | 是 | 交易日期 YYYY-MM-DD | txn_date |
| txn_time | time | 否 | 交易时间 HH:MM:SS | txn_time |
| currency | string(3) | 是 | 币种 ISO4217（缺省 CNY） | currency |
| amount | decimal | 是 | 金额**恒正**，方向见 dc_flag | amount |
| dc_flag | string(1) | 是 | `D`=借方/支出、`C`=贷方/收入（口径 C3 待财务确认） | dc_flag |
| counterparty_name | string | 是 | 对方户名 | counterparty_name |
| counterparty_account | string | 否 | 对方账号 | counterparty_account |
| summary | string | 否 | 摘要 | summary |

**扩展字段**：额外 key 允许出现，会随原始流水原样归档进 `ods_bank_raw_flow.raw_content`，不阻断标准字段落库（`ext_json` 后续承接）。

## 三、批次元数据（落库请求头）

```json
{
  "batch_no":          "B20260824-0001",
  "source_type":       "MOCK",
  "bank_id":           1,
  "account_id":        1,
  "source_ref":        "mock://cmb/2026-08-24",
  "contract_version":  "v1",
  "flow_date_start":   "2026-08-24",
  "flow_date_end":     "2026-08-24",
  "imported_by":       "system"
}
```

| 字段 | 取值 | 说明 |
|-|-|-|
| batch_no | 唯一字符串 | 业务批次号，格式建议 `B{YYYYMMDD}-{序号}`；全表唯一 |
| source_type | MOCK / FILE / API | 数据源类型，做切换留痕 |
| bank_id / account_id | 维表外键 | 与 `dim_bank` / `dim_bank_account` 一致 |
| source_ref | 任意 | 文件路径 / 接口 URI / Mock 标识 |
| contract_version | v1 | 契约版本，向后兼容 |
| flow_date_start/end | date | 本批流水日期范围 |

## 四、落库事务顺序（硬约束）

`ods_flow` 与 `dwd_trans_flow` 为**双向逻辑引用**（`ods.record_id ↔ flow.raw_id`），刻意不建物理 FK 以避免循环约束。落库必须按此顺序，`sp_ingest_flow` 已实现：

```
1. 建批次     dwd_flow_batch（IMPORTING）
2. 原始归档   ods_bank_raw_flow（appendix-only，先落原样 JSON）
3. 幂等去重   命中 dedup_key → 写 R001 留痕，跳过主表
4. 标准化     dwd_trans_flow（VALIDATING/PENDING）
5. 回填        ods.record_id = flow.record_id（双向溯源闭合）
6. 校验留痕   dwd_flow_validation（逐规则 R002/R003/R005）
7. 回写状态    validation_status / exception_type / process_status
8. 批次汇总   dwd_flow_batch.total_count/total_amount/status=VALIDATED
9. 审计留痕   aud_audit_log（哈希链）
```

---

## 五、幂等与重复处理

- `dedup_key = SHA256(bank_id|account_id|txn_no|txn_date|amount|dc_flag)`，`dwd_trans_flow` 唯一索引 `uk_dedup`。
- 重复命中（同批或跨批）→ 不二次入主表，写 `R001 FAIL` 留痕到已存在 record，`duplicate_count + 1`。
- 原始层**始终归档**（append-only），保证「本批收到什么」可完整回溯 —— 对账差异由 `v_recon_balance` 的 `count_diff` 显性暴露。

## 六、落库响应（返回给适配器 / 调用方）

```json
{
  "batch_id":         1001,
  "batch_no":         "B20260824-0001",
  "received_count":   100,
  "loaded_count":     98,
  "duplicate_count":  2,
  "failed_count":     1,
  "warn_count":       0
}
```

`sp_ingest_flow` 的 6 个 OUT 参数即此结构。语义：
- `received_count` = 适配器实际交给中台的条数（= 批次 total_count）
- `loaded_count` = 去重后新写入主表条数
- `duplicate_count` = R001 命中数
- `failed_count` = 校验 FAIL 条数（R002/R003/R005）
- `warn_count` = 校验 WARN 条数（R004 后置，一期默认 0）

---

## 七、状态机（provisional，待复核/推送规则定稿）

| validation_status | 触发 | process_status 去向 |
|-|-|-|
| FAIL | 命中 R002/R003/R005 | `LOADED`（不进复核，转异常处理） |
| PASS | 无异常规则 | `REVIEW_READY`（进入复核工作台） |
| WARN | 命中 R004（后置） | `REVIEW_READY`（预警提示，需人工复核） |

> 复核通过 → `REVIEW_PASSED` → 推送 → `PUSHED` → 制证回写 → `KINGDEE_POSTED`；驳回 → `REJECTED`。完整状态流转由全栈（复核台）+ 财务（规则）确认后固化，数据层字段已预留。
