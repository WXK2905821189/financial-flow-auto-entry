## 2. 认证方式选型（Decide）

金蝶星空 OpenAPI 为 **HTTP+JSON（RESTful）**，官方提供 **.NET / Java / Python 三种 SDK**；开放平台 `open.kingdee.com`（授权）与 `openapi.open.kingdee.com`（接口/SDK）。见 E1/E3。

**两条路径对比（推荐 B，兼顾本项目约定）：**

| 路径 | 说明 | 优劣 |
|---|---|---|
| A. 官方 Python SDK | 封装签名/登录/token，最省力 | 引入外部依赖，与「零外部依赖」约定需评审；官方维护 |
| **B. 自实现 HTTP + HMAC-SHA256（推荐）** | 仅用 `requests`，自己拼签名与 token | 零外部依赖、链路可控、与 D1「API 请求头签名」互为印证（E2） |

> 决策建议：一期先按 B 落地（可控、契合内网零依赖）；若后续金蝶侧字段/版本复杂导致维护成本高，再评估切官方 Python SDK。**此项需产品评审后锁定。**

## 3. 对接流程（时序）

```
1 第三方系统登录授权（open.kingdee.com）
   用户点授权 → 获取授权码(AuthorizationCode)
2 换取 AccessToken（携 appId/appSecret + 授权码）
3 调用接口：拼接 access_token 参数
   制证 BatchSave / 查单 ExecuteBillQuery / 提交·审核 Audit、Submit
```

**不依赖 SDK 的签名要点（E2）**：
- 准备：随机数 nonce、时间戳 ts；
- 拼待签名字符串 → **HMAC-SHA256** → 转 Hex → 再 Base64 → 放入请求头；
- 金蝶侧校验通过后返回 data（ExecuteBillQuery 结果含 fields 数组，下标取值）。

## 4. 制证端点与字段（BatchSave）

本项目相关接口子集（完整 18 标准接口以官方开放平台接口文档为准，E3）：
- `BatchSave`：记账凭证批量保存（**自动制证主端点**）
- `ExecuteBillQuery`：查单/复核结果回读
- `Save / Submit / Audit`：保存、提交、审核

**BatchSave 记账凭证字段（示例 · UAT 前以官方报文 + 账套科目校准）**

```jsonc
{
  "Model": {
    "BillNo": "{voucher_no}",
    "TDate": "2026-08-25",
    "FYear": "2026", "FPeriod": "08",
    "FSerialNum": "1",
    "FVoucherGroupID": {"FNumber": "<凭证字-张表手册>"},
    "Entry": [
      {
        "FExplanation": "<摘要>",
        "FAccountID": {"FNumber": "<科目编码>"},   // 由科目预填/映射给出
        "FDetailID": {"FNumber": "<核算维度-如往来单位>"},
        "FCurrencyID": {"FNumber": "PRE001"},       // 人民币
        "FAmount": "1000.00",                       // 本位币金额
        "FExchangeRate": "1",
        // 借贷方向由行内费用/应收应付区分，金蝶以科目方向+金额正负表达
      }
    ]
  }
}
```

> ⚠️ 以上为**待校准示例**，不构成最终报文。正式对接前必须：① 在 `openapi.open.kingdee.com` 用上真实测试账套在线测试 BatchSave；② 对照 D2 接口说明书 `V6.0` 的字段全集逐项核对。

## 5. 科目匹配接入（与 P1 预填衔接）

- **我方侧**：`services/account_mapper.py` 输出的 `ext_json.auto_subject`（科目编码/名称）作为 BatchSave 的 `FAccountID.FNumber` 来源；规则表 `dim_account_mapping` 由财务为 P4/UAT 维护。
- **金蝶侧**：可参考 F6「凭证模板」三取值（固定值/科目影响因素/单据科目字段），把部分科目判定下沉到金蝶，减少我方映射面；此决策与 P1/P4 联动，待财务确认科目口径后定夺。
- 匹配手段可参考 F1（AccountMatcher 关键词/语义）、F2/F3（对方户名+收支类型智能匹配）。

## 6. 工程约束落地（对齐本项目约定）

| 约束 | 落地方式 |
|---|---|
| 零外部依赖 | 自实现签名，仅 `requests` |
| 凭据不入库/不写死 | `KINGDEE_*` 走环境变量/内网密钥服务；本会话只读已确认无泄露 |
| 多账套/多用户 | 参考 D1 `AppSettingsModel`：以参数注入对象初始化，不静态配置 |
| 幂等/去重 | 沿用 `record_id ↔ voucher_no` 双向绑定；同 record 重推不重复制证 |
| 失败重试 | 接口抖动指数退避；半失败批次可重放恢复（与采集侧一致） |
| 切换开关 | `KINGDEE_MOCK_ENABLED` 保留——凭据未就绪走 Mock，就绪即切真实；真实侧结果回写审计留痕 |
| 审计溯源 | 真实推送也写入 `aud_audit_log` 与 `push` 表，保持哈希链与双向溯源 |

## 8. 验证方式

1. **单元**：签名函数（HMAC-SHA256 与官方示例向量对拍）；token 换发流程用 mock server 模拟金蝶响应。
2. **集成**：`smoke_test.py` 加真实推送分支（`KINGDEE_MOCK_ENABLED=false` + 测试凭据）。
3. **UAT**：真实账套创建→审核→对账，比对 `v_recon_*` 口径。
4. **回滚**：`KINGDEE_MOCK_ENABLED=true` 一键切回 Mock，不影响其余链路。

## 9. 风险

- 官方接口文档/版本随时间变化（E5 时间线）→ 以开放平台在线测试为准，仅将稳定字段固化进代码。
- 科目口径未冻结前自动制证存在坏账风险 → 真实侧先小批量试跑，经人工复核（human-in-the-loop）放量。
- 依赖被挂起的凭据待办 → 三步并行：先写代码+单测（不阻塞），凭据就绪即联调。
